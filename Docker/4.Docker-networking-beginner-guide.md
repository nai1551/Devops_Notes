# Docker Networking — A Beginner's Guide

Docker networking controls one simple question: **which containers can talk to each other, and how do they find each other?** This guide covers the theory first, then walks through hands-on practice for every concept.

---

## 1. Why Networking Exists in Docker

Every container is isolated by default — its own tiny filesystem, its own processes, and its own network stack. Without networking, two containers couldn't talk to each other even while running on the same machine. Docker's networking layer is what decides:

- Which containers can see each other
- How they find each other (by name, or only by IP)
- What's reachable from outside the machine at all

---

## 2. The Network Types (Drivers)

| Driver | What it does | When you'd use it |
|---|---|---|
| **bridge** | The default type. Creates a private internal network; containers on it can talk to each other, and you choose what's exposed to the outside world with `-p` | Almost all everyday Docker use |
| **host** | The container shares the host machine's network directly — no isolation, no port mapping needed | Rare — used when you specifically don't want network isolation |
| **none** | No network at all — fully isolated, nothing in, nothing out | Tasks that should never make any network call, for security |
| **overlay** | Connects containers across *multiple physical machines* | Docker Swarm / multi-host clusters — not relevant for a single machine |

Almost everything you'll do day to day uses **bridge** networking.

---

## 3. The Most Important Concept: Default Bridge vs. Custom Bridge

Docker automatically creates a network called `bridge` that every container joins if you don't specify one. It has one major limitation:

> **Containers on the default bridge can only reach each other by IP address — never by container name.**

A **custom bridge network** (one you create yourself with `docker network create`) fixes this. Any container explicitly attached to it can reach every other container on that same network **by name**, using Docker's built-in DNS.

This is the single biggest practical reason to always create your own network rather than relying on the default one — it's what lets code like `mysql.connector.connect(host="db-container")` work at all.

## 4. Practice — Proving Each Concept Yourself

### Step 1: See the built-in networks

```bash
docker network ls
```

You'll already see `bridge`, `host`, and `none` — Docker creates these automatically.

### Step 2: See the default bridge's limitation

Run two containers without specifying any network:

```bash
docker run -d --name alpha busybox sleep infinity
docker run -d --name beta busybox sleep infinity
```

(`busybox` is used here instead of a Python image because it includes basic networking tools like `ping` out of the box.)

```bash
docker exec -it alpha sh
ping beta
```

**Expected: this fails** — `ping: bad address 'beta'`. This proves the limitation directly: on the default bridge, containers cannot find each other by name.

Now try by IP instead:
```bash
exit
docker inspect beta | grep IPAddress
```
Copy the IP shown, then:
```bash
docker exec -it alpha sh
ping <beta's-ip>
exit
```

This should succeed — proving the containers genuinely *can* reach each other, just not by name on the default network.

```bash
docker rm -f alpha beta
```

### Step 3: Create a custom network and see the difference

```bash
docker network create practice-net
docker network ls
```

Confirm `practice-net` now appears in the list.

```bash
docker run -d --name alpha --network practice-net busybox sleep infinity
docker run -d --name beta --network practice-net busybox sleep infinity
```

```bash
docker exec -it alpha sh
ping beta
exit
```

**Expected: this now works.** This is the core lesson of the whole module — a custom bridge network gives you name-based DNS resolution that the default one doesn't.

### Step 4: Inspect the network to see what's happening underneath

```bash
docker network inspect practice-net
```

Look for:
- `"Subnet"` — the IP address range Docker is drawing from for this network
- `"Containers"` — both `alpha` and `beta` listed, each with their own assigned IP

### Step 5: Prove isolation between separate networks

```bash
docker network create isolated-net
docker run -d --name gamma --network isolated-net busybox sleep infinity
```

```bash
docker exec -it alpha sh
ping gamma
exit
```

**Expected: this fails.** `gamma` is on a completely different network (`isolated-net`). Even though it's running on the same physical machine, `alpha` cannot see it — this proves networks genuinely isolate groups of containers unless they're deliberately connected.

### Step 6: Connect a running container to a second network

A container isn't locked into one network forever — you can add it to another network without recreating it:

```bash
docker network connect practice-net gamma
docker exec -it alpha sh
ping gamma
exit
```

**Expected: this now works.** `gamma` is now on both `isolated-net` and `practice-net` at the same time — proving a single container can belong to multiple networks simultaneously.

### Step 7: Disconnect and confirm isolation returns

```bash
docker network disconnect practice-net gamma
docker exec -it alpha sh
ping gamma
exit
```

**Expected: fails again.** Networking isn't fixed at container creation — it can be managed dynamically while a container is running.

### Step 8: The `host` network — zero isolation

```bash
docker run -d --name hosttest --network host nginx:alpine
```

Notice: **no `-p` flag used at all.**

```bash
curl http://localhost:80
```

This works immediately — the container isn't isolated onto its own network at all, it's directly using the host machine's network stack. Rarely used in real projects since it removes Docker's isolation benefits, but useful to see once.

```bash
docker rm -f hosttest
```

### Step 9: The `none` network — total isolation

```bash
docker run -d --name notouch --network none busybox sleep infinity
docker exec -it notouch sh
ping google.com
```

**Expected: fails immediately.** No network access at all — not even to the internet. Used for tasks that should never be able to make any network call, purely for security.

```bash
exit
docker rm -f notouch
```

### Step 10: Clean up

```bash
docker rm -f alpha beta gamma
docker network rm practice-net isolated-net
docker network ls
```

Confirm only the built-in `bridge`, `host`, and `none` remain.

## 5. Quick Reference

| Command | What it does |
|---|---|
| `docker network ls` | List all networks |
| `docker network create <name>` | Create a custom bridge network |
| `docker network inspect <name>` | See subnet, gateway, and connected containers |
| `docker network rm <name>` | Delete a network (must have no containers attached) |
| `docker network connect <network> <container>` | Attach a running container to an additional network |
| `docker network disconnect <network> <container>` | Remove a running container from a network |
| `docker run --network <name> ...` | Start a new container already attached to a specific network |
| `docker run --network host ...` | Run with no network isolation — shares the host's network directly |
| `docker run --network none ...` | Run with no network access at all |

---

## 6. Common Mistakes

| Mistake | What happens | Fix |
|---|---|---|
| Running containers without `--network`, then expecting name-based communication | `ping: bad address` | Always create and use a custom bridge network for anything that needs to talk to another container by name |
| Assuming all containers can see each other by default | Only containers on the *same* network can — separate networks are fully isolated | Explicitly attach every container that needs to communicate to the same custom network |
| Using `--network host` "to make networking simpler" | Removes container isolation entirely, can cause port conflicts with the host | Reserve `host` networking for specific, deliberate cases — not general use |
| Forgetting a container is still on its *old* network after `docker network connect` to a new one | Unexpected connectivity to something not intended | A container can be on multiple networks at once — check with `docker network inspect` on each network to confirm exactly what's attached |

---

## 7. Key Takeaway

By default, Docker containers are isolated and can't find each other at all. A **custom bridge network** is what turns a group of separate containers into a system that can talk to each other **by name** — this one concept is the foundation every multi-container Docker project (a web app + database, a proxy + backend, anything with more than one moving part) is built on.
