# Docker Volumes & Bind Mounts — A Beginner's Guide

Both Volumes and Bind Mounts solve the same core problem — making data survive outside a container's own lifecycle — but they do it in different ways, for different purposes. This guide covers the theory for both, then hands-on practice for each, followed by a direct comparison.

---

## 1. The Problem They Both Solve

By default, everything a container writes lives inside its own temporary writable layer. The moment you run:

```bash
docker rm my-container
```

that data is gone permanently. For a throwaway script, that's fine. For a database, uploaded files, or config you want to keep editing, that's a real problem.

Docker offers two solutions: **named volumes** and **bind mounts**. Both keep data alive outside the container — they just differ in *who controls where that data actually lives*.

---

## 2. The Core Difference, Up Front

| | Named Volume | Bind Mount |
|---|---|---|
| Who picks the storage location? | **Docker** decides — a hidden path, usually under `/var/lib/docker/volumes/` | **You** decide — any real folder on your machine |
| How you reference it | By name: `db-data:/var/lib/mysql` | By real path: `~/site:/usr/share/nginx/html` |
| Can you browse it directly? | Not easily — tucked away in Docker's internal storage | Yes — it's a normal folder you already had access to |
| Typical use | Databases, app state Docker should fully manage | Live code editing, config files, anything you want direct control over |
| Live sync (host ↔ container) | Yes | Yes |
| Survives container removal | Yes | Yes (it was never "inside" the container to begin with) |

**The simplest way to think about it:**
- **Volume** = "Docker, please keep this data safe somewhere — I don't need to know exactly where."
- **Bind mount** = "Here's a specific folder I already own — let the container see straight into it."

## 3. PART A — Named Volumes

### 3.1 Basic commands

```bash
docker volume create <name>      # create a volume
docker volume ls                  # list all volumes
docker volume inspect <name>      # see its real location, driver, labels
docker volume rm <name>           # delete it (fails if in use)
docker volume prune               # delete all unused volumes
```

### 3.2 Practice — Persistence with MySQL

**Step 1: Create the volume**
```bash
docker volume create db-data
```

**Step 2: Run MySQL, mounting the volume to its data directory**
```bash
docker run -d \
  --name db-container \
  -e MYSQL_ROOT_PASSWORD=rootpass \
  -e MYSQL_DATABASE=mydb \
  -v db-data:/var/lib/mysql \
  mysql:8
```

`-v db-data:/var/lib/mysql` means: "mount the volume named `db-data` at this exact path inside the container" — which happens to be where MySQL stores its data files.

**Step 3: Add some data**
```bash
docker exec -it db-container mysql -u root -prootpass mydb
```
```sql
CREATE TABLE notes (id INT AUTO_INCREMENT PRIMARY KEY, message VARCHAR(255));
INSERT INTO notes (message) VALUES ('This should survive!');
EXIT;
```

**Step 4: Destroy the container completely**
```bash
docker stop db-container
docker rm db-container
```

**Step 5: Recreate it, same volume**
```bash
docker run -d \
  --name db-container \
  -e MYSQL_ROOT_PASSWORD=rootpass \
  -e MYSQL_DATABASE=mydb \
  -v db-data:/var/lib/mysql \
  mysql:8
```

**Step 6: Confirm the data is still there**
```bash
docker exec -it db-container mysql -u root -prootpass mydb -e "SELECT * FROM notes;"
```

Your row is still there — proof the volume kept the data independent of the container.

### 3.3 See where a volume actually lives

```bash
docker volume inspect db-data
```

Look for `"Mountpoint"` — something like `/var/lib/docker/volumes/db-data/_data`. That's the real location on your host, even though you never had to think about it while using the volume by name.

### 3.4 Anonymous volumes — know them, avoid them

```bash
docker run -d -v /var/lib/mysql mysql:8
```

No name before the colon — Docker still creates a real volume, but with a random hash-like name. It's hard to reference later and gets easily abandoned. Always prefer named volumes.

### 3.5 Cleanup

```bash
docker stop db-container
docker rm db-container
docker volume rm db-data
```

## 4. PART B — Bind Mounts

### 4.1 The syntax

```bash
docker run -v <host_path>:<container_path> <image>
```

`<host_path>` is a real, absolute (or `~`-relative) path on your machine. Everything already at `<container_path>` inside the image gets hidden by whatever's in `<host_path>` while the mount is active.

### 4.2 Practice — Live editing with Nginx

**Step 1: Create a folder and a file on the host**
```bash
mkdir -p ~/bindmount-practice/site
cd ~/bindmount-practice/site
nano index.html
```

```html
<!DOCTYPE html>
<html>
<head><title>Bind Mount Test</title></head>
<body>
  <h1>Version 1 — served from the host</h1>
</body>
</html>
```

**Step 2: Run Nginx, bind-mounting your folder in**
```bash
docker run -d \
  --name nginx-bind \
  -p 8082:80 \
  -v ~/bindmount-practice/site:/usr/share/nginx/html \
  nginx:alpine
```

**Step 3: Confirm it's serving your file**
```bash
curl http://localhost:8082
```
Expected: "Version 1 — served from the host", not Nginx's default page.

**Step 4: Edit the file on the host — container still running**
```bash
nano ~/bindmount-practice/site/index.html
```
Change to:
```html
<h1>Version 2 — updated live, no rebuild!</h1>
```

**Step 5: Just refresh — no Docker command needed**
```bash
curl http://localhost:8082
```
Expected: "Version 2" appears immediately. No restart, no rebuild.

**Step 6: Prove it works the other way — container writes, host sees it**
```bash
docker exec -it nginx-bind sh
echo "<h1>Version 3 — written from inside the container</h1>" > /usr/share/nginx/html/index.html
exit
```
```bash
cat ~/bindmount-practice/site/index.html
```
Expected: "Version 3" — proving the sync is genuinely two-way.

**Step 7: Clean up**
```bash
docker stop nginx-bind
docker rm nginx-bind
```

The `~/bindmount-practice` folder stays untouched — a bind mount was never "inside" the container's lifecycle.

## 5. Advanced: Things That Apply to Both

### 5.1 Read-only mounts

Either type can be mounted read-only, so a container can see data but never modify it:

```bash
docker run -v db-data:/var/lib/mysql:ro mysql:8
docker run -v ~/site:/usr/share/nginx/html:ro nginx:alpine
```

Adding `:ro` after the container path blocks writes from inside the container.

### 5.2 Sharing one volume across two containers

```bash
docker volume create shared-data

docker run -d --name writer -v shared-data:/data busybox sh -c "while true; do date >> /data/log.txt; sleep 5; done"

docker run -it --name reader -v shared-data:/data busybox cat /data/log.txt
```

`reader` sees exactly what `writer` is writing — same volume, two containers, no network involved at all.

### 5.3 Backing up and restoring a volume

Since a volume isn't a simple folder you can casually `cp`, the standard trick is a temporary helper container:

**Backup:**
```bash
mkdir -p ~/backup
docker run --rm -v db-data:/data -v ~/backup:/backup \
  busybox tar czf /backup/db-data-backup.tar.gz -C /data .
```

**Restore:**
```bash
docker run --rm -v db-data:/data -v ~/backup:/backup \
  busybox tar xzf /backup/db-data-backup.tar.gz -C /data
```

## 6. Common Mistakes

| Mistake | What happens | Fix |
|---|---|---|
| Forgetting `-v` entirely on a database container | Data vanishes on `docker rm` | Always mount a volume for anything stateful |
| Using an anonymous volume by accident (no name before `:`) | Data persists, but under an unmemorable random name | Always write `volume-name:/path`, never just `/path` |
| Running `docker volume prune` without checking first | Can silently delete volumes not currently attached to a running container | Check `docker volume ls` and `docker ps -a` first |
| Bind-mounting a path that doesn't exist yet | Docker silently creates it as an **empty directory** instead of failing | Always create the real file first, then mount it — check with `ls -la` after mounting if something seems wrong |
| Expecting a bind mount to publish a port | Files sync correctly but the app is still unreachable | Mounts handle *files*; you still need `-p host:container` for network access |
| Confusing which type you're using | Expecting to find volume data at a path you chose | Only bind mounts let you pick the host path — volumes live wherever Docker decides (`docker volume inspect` to check) |

## 7. Quick Command Reference

```bash
# Named volumes
docker volume create <name>
docker volume ls
docker volume inspect <name>
docker volume rm <name>
docker volume prune
docker run -v <volume-name>:<container-path> <image>

# Bind mounts
docker run -v <host-path>:<container-path> <image>

# Both support read-only
docker run -v <source>:<container-path>:ro <image>

# Backup/restore a volume
docker run --rm -v <volume>:/data -v <host-backup-folder>:/backup \
  busybox tar czf /backup/backup.tar.gz -C /data .
docker run --rm -v <volume>:/data -v <host-backup-folder>:/backup \
  busybox tar xzf /backup/backup.tar.gz -C /data
```

---

## 8. When to Use Which

| Use a **Volume** when... | Use a **Bind Mount** when... |
|---|---|
| The data belongs to the container/app (a database's files) | You need direct, easy access to the files yourself |
| You don't need to browse the raw files yourself | You're actively developing and want live code/config editing |
| You want Docker to fully manage naming, location, and cleanup | You already have a specific folder you want the container to see into |
| Portability matters (volumes behave the same across different host OSes) | You're mounting a config file another tool (like Jenkins) also needs to edit |

---

## 9. Key Takeaway

Both Volumes and Bind Mounts keep data alive outside a container's lifecycle — the real question is just **who should own the file path**. If the answer is "Docker, I don't need to touch it directly," use a volume. If the answer is "me, I want to edit these files myself," use a bind mount.
