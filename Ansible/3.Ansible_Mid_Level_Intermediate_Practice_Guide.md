## 2. Recommended Project Structure

> **In short:** instead of one big playbook file, organize your project into folders so config, secrets, variables, and roles each have a clear home. This is the layout professional Ansible projects use.

For intermediate practice, move from a single playbook into a project structure:

```text
ansible/
├── ansible.cfg
├── inventory
├── site.yml
├── group_vars/
│   └── workers.yml
├── host_vars/
│   └── worker1.yml
├── playbooks/
│   ├── nginx.yml
│   └── users.yml
├── roles/
│   └── nginx/
│       ├── defaults/
│       │   └── main.yml
│       ├── files/
│       ├── handlers/
│       │   └── main.yml
│       ├── meta/
│       │   └── main.yml
│       ├── tasks/
│       │   ├── main.yml
│       │   └── security.yml
│       ├── templates/
│       │   └── nginx.conf.j2
│       └── vars/
│           └── main.yml
└── secrets/
    └── vault.yml
```

A useful mental model — variables flow down from the inventory into the playbook, and the playbook hands off to a role, which is made up of its own tasks, handlers, templates, files, and variables:

```text
inventory
   |
   +--> group_vars
   |
   +--> host_vars
   |
   v
playbook
   |
   v
role
   |
   +--> tasks
   +--> handlers
   +--> templates
   +--> files
   +--> variables
```

## 3. Handlers

### 3.1 What is a handler?

A handler is a special task that runs **only** when another task notifies it — think of it as an "if something changed, then do this" trigger. It's typically used to restart or reload a service, but only when that service's configuration actually changed.

```text
Configuration changed
        |
        v
notify handler
        |
        v
reload/restart service
```

This prevents unnecessary service restarts, which matters in production because restarting a service can briefly interrupt traffic.

---

### 3.2 Create a handler

File: `roles/nginx/handlers/main.yml`

Create the folder (if it doesn't exist yet) and open the file in vim:

```bash
mkdir -p roles/nginx/handlers
vim roles/nginx/handlers/main.yml
```

Press `i` to enter insert mode, type/paste the content below, then press `Esc` followed by `:wq` and Enter to save and quit:

```yaml
---
- name: Restart nginx
  ansible.builtin.service:
    name: nginx
    state: restarted
```

Task that triggers it:

```yaml
- name: Deploy nginx configuration
  ansible.builtin.template:
    src: nginx.conf.j2
    dest: /etc/nginx/nginx.conf
  notify: Restart nginx
```

- If the template **changes**, the handler runs.
- If the template does **not** change, the handler does not run.

---

### 3.3 Reload instead of restart

For configuration changes, a reload is often preferable — it applies the new config without dropping active connections the way a full restart can.

Open the same handler file again to change it:

```bash
vim roles/nginx/handlers/main.yml
```

Replace the content with:

```yaml
---
- name: Reload nginx
  ansible.builtin.service:
    name: nginx
    state: reloaded
```

Then reference it from the task:

```yaml
notify: Reload nginx
```

---

### 3.4 Important behavior

If several tasks notify the same handler:

```text
Task A ---> notify Restart nginx
Task B ---> notify Restart nginx
Task C ---> notify Restart nginx
```

the handler normally runs **once**, at the end of the play — not once per notifying task. This is intentional: it avoids restarting nginx three times in a row when three tasks all touched its config.

## 4. files/ vs templates/

This distinction is very important, and a common early mistake is using the wrong one.

### 4.1 `files/`

Use `files/` for **static** files — content that never changes based on variables or the target host.

Example file: `roles/nginx/files/welcome.txt`

Create the folder and open the file in vim:

```bash
mkdir -p roles/nginx/files
vim roles/nginx/files/welcome.txt
```

Press `i`, type any plain text (e.g. `Welcome to the server!`), then `Esc` and `:wq` to save.

Task:

```yaml
- name: Copy static file
  ansible.builtin.copy:
    src: welcome.txt
    dest: /var/www/html/welcome.txt
    mode: "0644"
```

The file is copied byte-for-byte, without any Jinja2 processing.

---

### 4.2 `templates/`

Use `templates/` when the file needs to contain **variables or logic** that changes per host or environment.

Example file: `roles/nginx/templates/index.html.j2`

Create the folder and open the file in vim:

```bash
mkdir -p roles/nginx/templates
vim roles/nginx/templates/index.html.j2
```

Press `i`, paste the content below, then `Esc` and `:wq` to save:

```html
<!DOCTYPE html>
<html>
<body>
    <h1>Hi {{ user_name }}</h1>
    <p>Server: {{ ansible_hostname }}</p>
</body>
</html>
```

Task:

```yaml
- name: Deploy dynamic page
  ansible.builtin.template:
    src: index.html.j2
    dest: /var/www/html/index.html
```

---

### 4.3 Simple rule

```text
Static file
    |
    +--> copy + files/

Dynamic file
    |
    +--> template + templates/
```

## 5. Facts

### 5.1 What are facts?

Facts are information Ansible automatically gathers from managed nodes before running tasks — things like:

```text
hostname
OS
IP addresses
memory
CPU
interfaces
architecture
```

You can see the full list yourself by running:

```bash
ansible workers -m setup
```

This produces a large amount of data — don't worry about memorizing it, just know it exists and how to look it up.

---

### 5.2 Useful facts

Some of the most commonly used facts:

```yaml
{{ ansible_hostname }}
{{ ansible_distribution }}
{{ ansible_os_family }}
{{ ansible_default_ipv4.address }}
{{ ansible_processor_vcpus }}
{{ ansible_memtotal_mb }}
```

Example use:

```yaml
- name: Show server information
  ansible.builtin.debug:
    msg:
      - "Hostname: {{ ansible_hostname }}"
      - "OS: {{ ansible_distribution }}"
      - "Memory: {{ ansible_memtotal_mb }} MB"
      - "IP: {{ ansible_default_ipv4.address }}"
```

---

### 5.3 Disable fact gathering

Gathering facts takes a little time on every run. If a play doesn't need any facts, you can skip it to speed things up:

```yaml
- name: Simple task
  hosts: workers
  gather_facts: false
```

---

### 5.4 Facts + condition

Facts are often combined with `when` to make a task run only on the right kind of host:

```yaml
- name: Install nginx on Debian
  ansible.builtin.apt:
    name: nginx
    state: present
  when: ansible_os_family == "Debian"
```

## 6. register

`register` captures the result of a task into a variable so you can inspect or reuse it later in the playbook.

```yaml
- name: Check nginx version
  ansible.builtin.command: nginx -v
  register: nginx_version
  changed_when: false
```

Then inspect it:

```yaml
- name: Show nginx result
  ansible.builtin.debug:
    var: nginx_version
```

A registered result commonly contains fields such as:

```text
stdout
stderr
rc
changed
failed
```

---

### 6.1 Use register with a condition

```yaml
- name: Check a file
  ansible.builtin.stat:
    path: /tmp/test.txt
  register: test_file

- name: Show message if file exists
  ansible.builtin.debug:
    msg: "File exists"
  when: test_file.stat.exists
```

This "run a task, capture the result, decide what to do next" pattern is one of the most common patterns in real-world Ansible code:

```text
Task
  |
  v
register result
  |
  v
condition
  |
  v
next task
```

## 7. Conditionals

Conditionals control whether a task runs at all, using the `when` keyword.

### 7.1 Basic condition

```yaml
- name: Install nginx
  ansible.builtin.apt:
    name: nginx
    state: present
  when: ansible_os_family == "Debian"
```

**A common mistake:** don't wrap the condition in `{{ }}` — `when` already evaluates as an expression.

```yaml
# Wrong
when: "{{ ansible_os_family }} == 'Debian'"

# Correct
when: ansible_os_family == "Debian"
```

---

### 7.2 Multiple conditions

Listing several conditions means all of them must be true (a logical AND):

```yaml
when:
  - ansible_os_family == "Debian"
  - ansible_distribution_major_version | int >= 22
```

---

### 7.3 Variable condition

You can also condition a task on a plain boolean variable:

```yaml
vars:
  install_nginx: true

tasks:

  - name: Install nginx
    ansible.builtin.apt:
      name: nginx
      state: present
    when: install_nginx
```

---

### 7.4 `is defined`

Useful when a variable might not exist — for example, an optional setting that not every host provides:

```yaml
- name: Show optional variable
  ansible.builtin.debug:
    msg: "Environment is {{ environment }}"
  when: environment is defined
```

## 8. Loops

Loops let you run the same task against a list of values instead of writing the task out repeatedly.

### 8.1 Install multiple packages

```yaml
- name: Install packages
  ansible.builtin.apt:
    name: "{{ item }}"
    state: present
    update_cache: true
  loop:
    - nginx
    - git
    - curl
```

`item` represents the current value from the list on each pass through the loop.

---

### 8.2 Create directories

```yaml
- name: Create application directories
  ansible.builtin.file:
    path: "/opt/myapp/{{ item }}"
    state: directory
    mode: "0755"
  loop:
    - logs
    - config
    - data
```

---

### 8.3 Loop over dictionaries

Loops can also iterate over a list of dictionaries, so each `item` has multiple fields:

```yaml
- name: Create users
  ansible.builtin.user:
    name: "{{ item.name }}"
    shell: "{{ item.shell }}"
    state: present
  loop:
    - name: devops
      shell: /bin/bash
    - name: deploy
      shell: /bin/bash
```

---

### 8.4 Loop + variable

Instead of hardcoding the list in the task, store it as a variable and reference it — this keeps the task reusable:

```yaml
vars:
  packages:
    - nginx
    - git
    - curl

tasks:

  - name: Install packages
    ansible.builtin.apt:
      name: "{{ item }}"
      state: present
    loop: "{{ packages }}"
```

## 9. Variable Precedence

Ansible can receive the same variable name from several different places at once. **Precedence** is simply the rule for which value wins when that happens.

Important sources include:

```text
role defaults
inventory/group variables
host variables
play vars
task vars
extra vars
```

A useful simplified rule, from lowest to highest priority:

```text
defaults
   ↓
group_vars
   ↓
host_vars
   ↓
play/task variables
   ↓
extra vars (-e)
```

More specific values generally override less specific ones — a value set for one single host beats a value set for a whole group, and a value passed on the command line beats everything.

---

### 9.1 Example

Role default:

```yaml
# roles/nginx/defaults/main.yml

site_title: "Default Site"
```

Group variable:

```yaml
# group_vars/workers.yml

site_title: "Workers Site"
```

Host variable:

```yaml
# host_vars/worker1.yml

site_title: "Worker1 Site"
```

Command line:

```bash
ansible-playbook site.yml -e "site_title=Emergency Site"
```

Here, `-e` (extra vars) is the most specific and wins, so `site_title` becomes `"Emergency Site"` regardless of what the other three files say.

---

### 9.2 Why precedence matters

It lets the same role support multiple environments without rewriting it:

```text
Development
Staging
Production
```

You write the role once, then override values per environment using `group_vars`, `host_vars`, or `-e`.

## 10. group_vars

`group_vars` stores variables shared by every host in a group.

Structure: `group_vars/workers.yml`

```yaml
---
app_name: myapp
app_port: 8080
environment: development
```

Inventory:

```ini
[workers]
worker1 ansible_host=192.168.56.102 ansible_user=worker
worker2 ansible_host=192.168.56.103 ansible_user=worker
```

Both `worker1` and `worker2` automatically receive these variables because they're both in the `workers` group.

Use it in a task like this:

```yaml
- name: Show application configuration
  ansible.builtin.debug:
    msg: "{{ app_name }} runs on port {{ app_port }}"
```

---

## 11. host_vars

`host_vars` stores variables for **one specific host only**, overriding anything set at the group level.

Structure: `host_vars/worker1.yml`

```yaml
---
app_port: 8081
server_role: primary
```

Now `worker1` gets its own values, separate from the rest of the `workers` group. This is useful when hosts play different roles, for example:

```text
worker1 -> primary
worker2 -> secondary
```

## 12. ansible.cfg

`ansible.cfg` is Ansible's configuration file — it controls default behavior so you don't have to repeat the same command-line flags every time.

Example:

```ini
[defaults]
inventory = ./inventory
host_key_checking = False
retry_files_enabled = False
```

To check which configuration file Ansible is actually using, run:

```bash
ansible --version
```

The output includes the configuration file path it loaded.

---

### 12.1 Why configuration matters

Instead of repeatedly writing:

```bash
ansible -i inventory workers -m ping
```

you can set the inventory path once in `ansible.cfg`:

```ini
inventory = ./inventory
```

and from then on just run:

```bash
ansible workers -m ping
```

---

### 12.2 Important note

Disabling host key checking:

```ini
host_key_checking = False
```

can be convenient in a lab or throwaway environment, but understand the SSH security implications before using it in production — it removes a check that normally protects you against connecting to an unexpected or spoofed host.

## 13. Tags

Tags let you run only a chosen subset of tasks instead of the whole playbook — handy when you only need to re-run one part (like the config) without repeating everything else.

```yaml
tasks:

  - name: Install nginx
    ansible.builtin.apt:
      name: nginx
      state: present
    tags:
      - install

  - name: Deploy website
    ansible.builtin.template:
      src: index.html.j2
      dest: /var/www/html/index.html
    tags:
      - website

  - name: Start nginx
    ansible.builtin.service:
      name: nginx
      state: started
    tags:
      - service
```

Run only the website task:

```bash
ansible-playbook site.yml --tags website
```

Run only installation:

```bash
ansible-playbook site.yml --tags install
```

Skip a tag:

```bash
ansible-playbook site.yml --skip-tags website
```

List all tags available in a playbook:

```bash
ansible-playbook site.yml --list-tags
```

## 14. Debugging

### 14.1 debug module

Print the value of a variable:

```yaml
- name: Show variable
  ansible.builtin.debug:
    var: app_port
```

Or print a custom, formatted message:

```yaml
- name: Show custom message
  ansible.builtin.debug:
    msg: "Server {{ ansible_hostname }} uses port {{ app_port }}"
```

---

### 14.2 Verbose output

When something isn't working as expected, increasing verbosity shows more of what Ansible is doing behind the scenes.

```bash
ansible-playbook site.yml -v
```

More detail:

```bash
ansible-playbook site.yml -vv
```

Very detailed troubleshooting (connection-level detail):

```bash
ansible-playbook site.yml -vvv
```

Don't reach for `-vvv` on every run by default — it produces a lot of output and is best saved for actually diagnosing a problem.

---

### 14.3 Check syntax

Validate a playbook's YAML/Ansible syntax without running it:

```bash
ansible-playbook site.yml --syntax-check
```

## 15. Error Handling

### 15.1 `failed_when`

By default, Ansible treats certain exit codes as failures. `failed_when` lets you redefine what counts as a failure for a specific task.

```yaml
- name: Check application
  ansible.builtin.command: /usr/local/bin/check-app
  register: check_result
  failed_when: check_result.rc not in [0, 2]
```

Here, return codes `0` and `2` are both treated as acceptable — anything else fails the task.

---

### 15.2 `changed_when`

Some commands report as "changed" even though they didn't actually modify anything (this is common with the generic `command`/`shell` modules, since Ansible can't tell what they did). You can override that:

```yaml
- name: Check nginx version
  ansible.builtin.command: nginx -v
  register: nginx_version
  changed_when: false
```

This keeps the task's reported result accurate and idempotent-looking:

```text
changed: false
```

## 16. block / rescue / always

`block`, `rescue`, and `always` give you structured error handling — similar to try/catch/finally in a programming language.

```yaml
- name: Application deployment
  block:

    - name: Copy application file
      ansible.builtin.copy:
        src: app.conf
        dest: /etc/myapp/app.conf

    - name: Restart application
      ansible.builtin.service:
        name: myapp
        state: restarted

  rescue:

    - name: Show deployment failure
      ansible.builtin.debug:
        msg: "Application deployment failed"

  always:

    - name: Deployment finished
      ansible.builtin.debug:
        msg: "Deployment process completed"
```

Execution flow:

```text
block
  |
  +--> success --> continue
  |
  +--> failure --> rescue
                     |
                     v
                   always
```

`rescue` only runs if something in `block` fails. `always` runs no matter what happened.

## 17. import_tasks and include_tasks

Both let you split a long task list into multiple smaller files, which keeps things organized and reusable.

```text
tasks/
├── main.yml
├── install.yml
└── configure.yml
```

### 17.1 import_tasks

```yaml
- import_tasks: install.yml
- import_tasks: configure.yml
```

This is a **static** import — Ansible resolves it before the play even starts running, so it can't depend on a variable or condition that's only known at runtime.

---

### 17.2 include_tasks

```yaml
- include_tasks: "{{ task_file }}.yml"
```

This is **dynamic** — it's resolved while the playbook is running, so it can depend on variables or conditions, like choosing which file to load based on the OS:

```yaml
- name: Include Debian tasks
  ansible.builtin.include_tasks: debian.yml
  when: ansible_os_family == "Debian"

- name: Include RedHat tasks
  ansible.builtin.include_tasks: redhat.yml
  when: ansible_os_family == "RedHat"
```

---

## 18. import_role and include_role

Roles can also be loaded explicitly from within a task list, rather than only from the `roles:` section of a play.

### 18.1 import_role

```yaml
tasks:

  - name: Load nginx role
    ansible.builtin.import_role:
      name: nginx
```

### 18.2 include_role

```yaml
tasks:

  - name: Load nginx role conditionally
    ansible.builtin.include_role:
      name: nginx
    when: install_nginx
```

Same static-vs-dynamic idea as tasks:

```text
import_role
    -> static

include_role
    -> dynamic
```

## 19. Role Dependencies

A role can automatically pull in another role it depends on, so you never forget to run a prerequisite.

File: `roles/nginx/meta/main.yml`

```yaml
---
dependencies:
  - role: common
```

Now, whenever the `nginx` role runs, the `common` role runs first automatically:

```text
nginx role
    |
    v
common role
```

This is useful when a role requires prerequisite configuration (for example, a `common` role that sets up base packages or users every other role expects to exist).

## 20. Idempotency

Idempotency is one of the most important Ansible concepts: **running the same playbook twice should produce the same end state, and the second run should report no changes** if nothing actually needed to change.

```yaml
- name: Install nginx
  ansible.builtin.apt:
    name: nginx
    state: present
```

First run:

```text
changed: true
```

Every run after that:

```text
ok
```

because nginx is already present and the module recognizes that.

---

### 20.1 Bad practice

Avoid using `shell`/`command` for something a dedicated module can already manage — the generic modules don't know how to check "is this already true?", so they tend to report `changed` on every single run.

Less ideal:

```yaml
- name: Install nginx
  ansible.builtin.shell: apt install nginx -y
```

Better:

```yaml
- name: Install nginx
  ansible.builtin.apt:
    name: nginx
    state: present
```

The dedicated `apt` module understands the desired state and only acts when needed.

## 21. Ansible Vault

Never put real passwords or API keys directly into Git-tracked plain-text files. Vault encrypts sensitive data so it's safe to commit.

### 21.1 Create a Vault file

```bash
mkdir -p secrets

ansible-vault create secrets/vault.yml
```

This opens an editor. Enter:

```yaml
---
db_username: appuser
db_password: StrongExamplePassword
```

Save and exit — the file is stored encrypted on disk.

---

### 21.2 View

```bash
ansible-vault view secrets/vault.yml
```

---

### 21.3 Edit

```bash
ansible-vault edit secrets/vault.yml
```

---

### 21.4 Encrypt an existing file

```bash
ansible-vault encrypt secrets/plain.yml
```

---

### 21.5 Decrypt

```bash
ansible-vault decrypt secrets/vault.yml
```

Be careful with decrypted secrets in shared repositories — re-encrypt before committing.

---

### 21.6 Use Vault variables

Reference the variables from a Vault file just like any other variable:

```yaml
- name: Show username
  ansible.builtin.debug:
    msg: "Database user is {{ db_username }}"
```

Run the playbook and supply the Vault password:

```bash
ansible-playbook site.yml --ask-vault-pass
```

The encrypted file can be loaded through `vars_files`:

```yaml
---
- name: Application setup
  hosts: workers

  vars_files:
    - secrets/vault.yml

  tasks:
    - name: Show database username
      ansible.builtin.debug:
        msg: "{{ db_username }}"
```

**Never** print real passwords with `debug` — this example is for a placeholder username only.

## 22. Check Mode and Diff

### 22.1 Check mode

Ask Ansible to predict what it *would* change, without actually applying anything — a "dry run":

```bash
ansible-playbook site.yml --check
```

This is useful for previewing changes before a real deployment.

---

### 22.2 Diff

## Glossary

Quick plain-language definitions for terms used throughout this guide.

| Term | Meaning |
|---|---|
| **Control node** | The machine you run Ansible commands from. |
| **Managed node** | A remote machine that Ansible configures (also called a "worker" or "host" in this guide). |
| **Inventory** | The file listing which hosts (and groups of hosts) Ansible can manage. |
| **Playbook** | A YAML file describing the desired state of one or more hosts, made up of plays and tasks. |
| **Task** | A single action Ansible performs, usually by calling a module (e.g. "install nginx"). |
| **Module** | The built-in unit of work Ansible uses to do something, e.g. `ansible.builtin.apt`, `ansible.builtin.copy`. |
| **Role** | A reusable, self-contained bundle of tasks, handlers, templates, files, and variables. |
| **Handler** | A task that only runs when explicitly notified by another task, typically to restart/reload a service. |
| **Fact** | Information Ansible automatically collects about a managed node (OS, IP, memory, etc.). |
| **Idempotent** | Safe to run repeatedly — running it again with no real change to make produces no change. |
| **`become`** | Tells Ansible to run a task with elevated privileges (like `sudo`). |
| **Jinja2** | The templating language Ansible uses for variables and logic inside `.j2` template files. |
| **Vault** | Ansible's built-in tool for encrypting sensitive files (passwords, keys) at rest. |
